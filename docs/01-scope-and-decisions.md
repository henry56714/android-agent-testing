# 01 需求、范围与技术选择

日期：2026-11-11。状态：待实施的技术设计；本文件的决策替代早期针对单一 App 的重型编排/数据库方案。

## 1. 用户目标

用户提供自然语言测试意图或完成代码修改后，Coding Agent 应能：

1. 理解变更与业务要求，识别受影响功能及风险。
2. 检索持久化用例库，优先复用并补齐缺失覆盖。
3. 保存代码检查配置、单元测试、设备逻辑测试或 Maestro flow。
4. 构建指定 APK，在指定设备执行，并保存结果和证据。
5. 下次会话或 CI 在不重新生成用例的情况下重放。
6. 同一套工具用于多个 Android App；接入新 App 主要是配置和业务测试，不修改通用核心。

“静态测试”内部区分静态检查与执行代码的单元测试，避免混淆测试能力和覆盖率。

## 2. 核心决策

| 决策 | 选择 | 原因 |
|---|---|---|
| UI 引擎 | Maestro CLI 与其内置 MCP | 直接使用现有 YAML、设备操作与 Agent 接口 |
| Android 代码检查/测试 | 项目 Gradle wrapper、现有 JUnit/AndroidX Test | 尊重工程原有技术栈，不强制迁移测试版本 |
| 系统控制与取证 | Android SDK 的 ADB 等工具 | 使用标准工具，按设备能力探测 |
| 自然语言解释 | 调用方 Coding Agent | 工具不绑定厂商、模型或模型 API Key |
| 工具实现 | 后续采用 Python 3.11+ 的薄 CLI，依赖锁定 | 文件索引、子进程管理、结果归一化；不是新的测试执行引擎 |
| 用例库 | YAML 元数据 + 原生测试文件 + Git | 可审查、可重放、无需服务端 |
| 数据库/检索服务 | 第一版不引入 | 目录扫描与过滤足够支撑首期，规模瓶颈出现后再评估 |
| 测试描述 | 原生 Maestro/JUnit/instrumentation + 人类可读契约 | 不创造一套需要编译到多个引擎的测试 DSL |
| Agent 连接 | 先用现有 shell 工具与 Maestro MCP | 第一版不新建 MCP 服务；以后可薄封装同一 CLI |

## 3. 能力与边界

| 层 | 示例 | 判定来源 |
|---|---|---|
| static | 编译、Lint、Manifest/资源/API 使用 | 结构化问题报告、明确的工具退出结果 |
| local | 参数、序列化、状态机、纯逻辑、可控并发 | JUnit XML 与断言 |
| device | Android 生命周期、线程、权限、JNI、服务/任务调度 | instrumentation 结果及必要的事件 |
| ui | 启动、操作、页面、完整业务入口 | Maestro 断言；必要时关联测试服务端结果 |

只有 APK 时，static/local/device 内部逻辑不能默认视为可用。工具必须说明不适用或能力缺失，不能因为 UI 通过就宣布内部线程正确。

首期正式验证目标：macOS/Linux 主机、Java/Kotlin Gradle 工程、Android 模拟器与 USB 真机。Windows、设备云、跨平台源码构建先标未验证。Android API 支持范围由工具版本、App minSdk/targetSdk、设备能力共同决定，不预先硬编码全局 API 范围。

## 4. 非目标

- 替代 Maestro/Appium、重写 Android UI 驱动。
- 自动证明全部并发交错、全部设备和全部业务场景正确。
- 仅靠截图识别内部逻辑是否正确。
- 第一版开发可视化管理平台、设备农场、账号服务或模型网关。
- 自动修改业务预期以让测试通过，或自动把失败用例移出门禁。

## 5. 通用性标准

应用包名、模块名、flavor、variant、构建命令、安装产物、启动 Activity、测试端点、业务阈值和测试探针都属于项目适配。通用层只知道任务、产物、用例、能力、设备和结果。

至少用两个结构不同的源码项目和一个 APK-only 场景验证。把第一个项目复制后改包名，不能充分证明通用性。
